# Creative Intelligence Layer

Stage 11A. Structured creative-planning artifacts that will eventually sit
BEFORE keyframes and video generation. This stage only stores creative
decisions — it never generates anything, never calls EvoLink, and never
spends a credit.

## The pipeline this stage is building toward

```
USER IDEA
    ↓
CREATIVE BRIEF
    ↓
MASTER CREATIVE SPECIFICATION
    ↓
VISUAL BIBLE
    ↓
STORYBOARD
    ↓
KEYFRAME PLAN
    ↓
HUMAN APPROVAL
    ↓
VIDEO GENERATION
```

This stage builds everything down to **Storyboard**. Keyframe planning,
human approval of a keyframe/video plan, and generation itself are all
later stages, deliberately not started here.

## Why structured data instead of one giant prompt

A single long prompt has no memory and no reusable parts: if you want the
same character's face consistent across ten shots, you either retype the
same description ten times (and it drifts a little each time) or you
don't bother, and the character visibly changes shot to shot. Structured
data fixes this by separating **what's true about the production**
(a character's identity, a location's architecture, the overall tone)
from **what a specific shot needs to say**. A shot references a character
by id instead of re-describing them — one place to define "Mira always
has a scar above her left eyebrow," reused everywhere she appears.

This is also literally required for the future pipeline in Part 12/13:
specialist skills and prompt builders need query-able facts (`what does
this character look like?`, `what's the lighting rule for this world?`),
not a wall of text they'd have to re-parse every time.

## The Creative Brief

The human-authored starting point (`schemas/creative-schema.js`'s
`createCreativeBrief`): what this project is, for whom, and why — title,
concept, premise, objective, audience, tone, genre, format, target
duration, visual direction, narrative approach, key message, constraints,
references, creative notes. One per project. Every field defaults to
`null`/`[]` — nothing here is ever invented on the system's behalf; it's
only ever what a human actually supplied.

## The Master Creative Specification

The stable, structured contract everything downstream reads from
(`createMasterCreativeSpec`) — deliberately **not** one giant prompt.
Fields like `coreConcept`, `storyLogic`, `tone`, `pacing`,
`visualLanguage`, `cinematography`, `lighting`, `colourLanguage`,
`environmentRules`, `characterRules`, `wardrobeRules`, `cameraRules`,
`motionRules`, `compositionRules`, `continuityRules`,
`negativeConstraints`, and `referenceStrategy` each capture one distinct
creative decision. `masterPrompt` is a field reserved for the derived
text representation described below — present so it can be filled in
later, but this stage never generates it automatically.

## The Visual Bible

The persistent visual rules of the production (`createVisualBible`), in
13 sections: world, characters, wardrobe, props, locations, architecture,
lighting, colour, camera, composition, texture/materials, atmosphere, and
continuity rules. `characters`, `props`, and `locations` are structured
arrays of their own record types (below); the rest are named rule fields
rather than one paragraph, so each concern (lighting rules vs. camera
rules vs. continuity rules) can be read, referenced, and updated
independently.

## Characters

Character consistency is one of this project's core objectives, so a
character (`createCharacter`) is a stable identity record, not prose
embedded in a shot: `characterId`, `name`, `role`, physical/facial/body
description, hair, skin, wardrobe, accessories, recurring props,
behaviour, `identityConstraints` (the "identity lock" — what must never
change about this character), continuity notes, and reference assets (for
when reference images exist — none are generated by this stage). A shot
in the storyboard references a character by id (`characterReferences`)
instead of re-describing them.

## Locations

The same idea applied to places (`createLocation`): `locationId`, name,
description, architecture, geography, materials, colour palette,
lighting, atmosphere, recurring elements, continuity constraints, and
reference assets. Multiple shots — even across different scenes — can
point at the same location definition, so "this hallway always looks like
this" is defined once.

A small `createProp` record exists for the same reason, for recurring
objects worth tracking consistently (a specific pocket watch, a specific
prop weapon) without needing a character's or location's full structure.

## The Storyboard

`createStoryboard` holds a project's creative-planning **scenes** and
**shots** — a richly-described, structured plan, not the production
Timeline IR used for actual generation jobs (see below). A storyboard
shot (`createStoryboardShot`) captures: `sceneId`, `order`, `duration`,
`purpose`, `narrativeBeat`, `visualDescription`, `subject`, `location`,
`action`, `camera`, `framing`, `lens`, `movement`, `lighting`,
`soundNotes`, `transition`, `continuityRequirements`, and references to
characters/locations/props/assets by id. `promptDraft` exists as a field
for later, but **the structured fields are the source of truth** — a
prompt is something derived from them, never the other way around.

`status` is a small, separate planning-status enum —
`DRAFT → PLANNED → READY_FOR_KEYFRAME → KEYFRAME_APPROVED →
READY_FOR_VIDEO → GENERATED` — tracking creative-planning progress only.
This is intentionally **not** the project state machine
(`schemas/state-machine.js`'s `PLANNING`/`GENERATION_REVIEW`/
`CALIBRATION`/… states) and not the existing Timeline IR shot's own
`status`/`approvalStatus` fields. Nothing in this stage moves a shot
through this enum automatically, and reaching `READY_FOR_VIDEO` here does
not — by itself — cause anything to generate.

### Storyboard vs. the existing Timeline IR

This project already has `project.scenes`/`project.shots` (Stage 5's
Timeline IR, in `schemas/production-schema.js`) — the shots that actually
get submitted to EvoLink. The Stage 11A storyboard is a **separate**,
richer, creative-planning-only structure, stored separately (see below).
A future stage will define how an approved storyboard shot turns into a
Timeline IR shot and, eventually, a generation request — this stage
deliberately stops before that mapping exists, so the two systems can't
be confused for each other or accidentally short-circuited into one.

## How they relate

```
Creative Brief  (why this project exists)
      ↓ informs
Master Creative Spec  (the structured contract)
      ↓ informs
Visual Bible  (persistent visual rules: characters, locations, props, ...)
      ↓ referenced by
Storyboard  (scenes and shots, referencing Visual Bible entries by id)
```

Nothing here is enforced by validation — a storyboard shot can reference
a `characterReferences` id that doesn't exist yet, the same way a draft
document can reference a section that hasn't been written. Consistency is
a creative-process discipline, not (yet) a database constraint.

## Storing creative decisions instead of one prompt

Each of the four top-level artifacts is versioned lightly
(`services/creative-store.js`): every deliberate update records
`version`, `updatedAt`, `updatedBy`, and `changeNote`, and pushes the
artifact's *previous* version metadata onto a `history` array before
applying the change. This is **not** Git — there's no branching, no
merging, and no full-content snapshots kept in history, only "what
changed, when, by whom, and why," which is enough to answer "why does
this say X now?" without building real version control. The artifact's
own top-level fields are always the current version — there's nothing
else to look up.

Creative artifacts persist as one JSON file per project under
`server/data/creative/<projectId>.json` (gitignored, same pattern as
`server/data/projects/` and `server/data/generation-jobs/`) — a project
has at most one Creative Brief, one Master Spec, one Visual Bible, and one
Storyboard, so one combined file per project is simpler than four.

## How Claude skills will eventually consume these artifacts

Nothing here hardcodes a specific skill's prompt format. The goal is that
a future orchestrator can read a project's Master Creative Spec + Visual
Bible + a specific storyboard shot, and hand exactly the structured facts
a specialist skill (e.g. a cinematography or worldbuilding skill) needs —
without that skill needing to know this project's internal schema, and
without this project needing to know that skill's internal prompt
templates. The MCP tools this stage adds (`get_creative_brief`,
`get_master_creative_spec`, `get_visual_bible`, `get_storyboard`, plus
their `update_*`/`create_storyboard_*` counterparts) are exactly that
read/write surface.

## The master-prompt relationship (Part 13)

```
STRUCTURED CREATIVE SPECIFICATION
            ↓
      MASTER PROMPT
            ↓
     SHOT-SPECIFIC PROMPT
```

The structured specification (Master Creative Spec + Visual Bible) is the
source of truth. `masterCreativeSpec.masterPrompt` and
`storyboardShot.promptDraft` are fields reserved for the two derived
levels below it — present in the schema so a future stage has somewhere
to put them, but this stage implements no automatic derivation. Nothing
here decides prompts on its own; that stays a deliberate future step.

## Why creative planning never spends a credit

Every function in `services/creative-store.js` only reads/writes a plain
JSON file under `server/data/creative/`. None of them import
`services/approval-gate.js`, `services/generation-service.js`, or
anything in `providers/evolink/` — there is no code path from a creative
update to a provider call, so "updating a storyboard accidentally
generates a video" isn't a bug this code could have; the two systems
simply aren't wired together yet. Human approval and the budget gate stay
exactly where Stage 3/8.1 put them, unchanged.

## How this eventually leads into keyframes and video generation

A later stage will read a storyboard shot marked `READY_FOR_VIDEO`,
resolve its character/location/prop references from the Visual Bible,
derive a shot-specific prompt (per the relationship above), create the
corresponding Timeline IR shot, and — only after a human approves it
through the existing Stage 3 approval/budget gate — call
`request_generation`, exactly the way the current pipeline already does
for the smoke-test shot. None of that wiring exists yet; this stage only
makes sure the creative decisions it will need are already stored,
structured, and versioned.
